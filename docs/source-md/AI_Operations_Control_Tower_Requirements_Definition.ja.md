# 文書の目的

AI Operations Control Tower のために、ソフトウェアエンジニアリングのバックログとしてそのまま使える要件ベースラインを定義します。この Control Tower は、運用関係者に一貫した運用上の唯一の情報源を提供し、例外とオーナーシップを明確に示し、非破壊的な what-if シミュレーションをサポートし、連携した 2D および 3D ビューによって、密度の高い空港運用の関係性を理解しやすくします。

# 1. ビジネスコンテキストとスコープ

出典資料には、SIOC、BU Ops、Ground Ops にまたがる可視性の分断、無線機/WhatsApp/電話による連携、例外検知の遅れ、アクションオーナーの不明確さ、DSM、DCT、G-Ops、Mosaic を並べて監視している状況が記述されています。目指す成果は、フライト、ターンアラウンド、スタッフ、機材、SLA リスクを 1 つの画面で把握でき、ロールに応じたドリルダウンと、責任の所在を追跡できるアクション履歴を備えることです。

# 2. プロダクト原則

* 1 つの運用ピクチャ: すべてのビューは、ブラウザー内の 1 つのプロトタイプデータモデルと、1 つのアクティブなフィルター/シミュレーションコンテキストから導出されなければならない。
* ロールへの適合性を保ちつつ、真実を分断しない: 各ロールには専用のレンズを提供するが、すべてのレンズは同じエンティティ ID、タイムスタンプ、ステータス、オーナーシップを参照する。
* ビュー優先のプロトタイプ: 操作は、フィルター、グループ化、ハイライト、比較、シミュレーションを行えるが、ソースの運用レコードを変更してはならない。
* 段階的な情報開示: まず全体像を示し、その後、運用コンテキストから離れることなく、ピア/航空会社/フライト/ターンアラウンド/タスク/アセットの詳細を表示する。
* 人間が理解できる複雑さ: 2D と 3D は別々のエクスペリエンスではなく、同じデータを連動して表現したものでなければならない。
* Microsoft のデザイン原則: 明瞭さ、階層、余白、アクセシブルな色の意味づけ、見慣れたコマンドパターン、レスポンシブなサーフェス、Fluent スタイルのインタラクション動作。

# 6. シミュレーター: 非破壊的な what-if 分析

シミュレーターは、プロトタイプのために追加した要件です。ソースのビジネスレコードとは意図的に分離されています。シナリオは、パラメーターの上書きと、計算された表示上の影響で構成されます。シナリオの適用、リセット、比較は、描画されるビューと派生インジケーターのみを変更します。

| **シナリオケース** | **有効なプロトタイプパラメーター** | **検証 / 動作** |
| --- | --- | --- |
| 到着便の遅延 | フライトの運航; 遅延分数 0-240; 影響を受けるピア/スタンド; 乗り継ぎの感度 Low/Med/High | 表示されるマイルストーンのタイミング、例外の重大度、SLA リスクのインジケーターのみを再計算する。 |
| 天候 / ランプ作業停止 | 開始オフセット; 継続時間 0-180 分; 影響を受けるゾーン; 重大度; 回復バッファー | 制約の時間帯と派生した影響をオーバーレイする。ソースのフライト/タスクのレコードは変更されない。 |
| GSE の不足 / 利用不可 | アセットの種類; 利用不可の数量 0..利用可能数; 影響を受けるピア/スタンド; 継続時間 | シミュレートされた可用性、依存するタスクのリスク、影響を受けるターンアラウンドを更新する。 |
| スタッフのキャパシティ減少 | BU/チーム; キャパシティの増減 0-100%; 有効な時間帯; オプションのスキルグループ | シミュレートされたキャパシティの逼迫度と、タスク/マイルストーンのリスクを更新する。 |
| SLA しきい値のストレス | 航空会社; SLA マイルストーン; しきい値の増減; 選択したフライト/時間枠 | ビュー比較のために、シミュレートされた SLA リスクの分類を再計算する。 |
| 複合的な障害 | 上記の互換性のある任意の組み合わせに、シナリオ名とメモを付与 | 競合の検証、シナリオのサマリー、影響を受けるエンティティ数、ベースライン対シナリオのビューを表示する。 |

# 13. プロトタイプのコンポーネントアーキテクチャ

* Web アプリケーションシェル: プロトタイプの UI には React/TypeScript を推奨します。コンポーネントライブラリは Fluent スタイルのパターンに従うものとします。
* ドメインストア: IndexedDB からハイドレートされた、正規化されたインメモリの状態。セレクターが、ロール/フィルター/シナリオごとの射影を生成します。
* シナリオエンジン: ベースラインのスナップショットと検証済みパラメーターを受け取り、派生した影響のオーバーレイを返す純粋関数。
* 2D レンダラー: レイヤーと安定したエンティティのヒットテストを備えた、ベクター/canvas/WebGL のマップ抽象化。
* 3D レンダラー: エンティティからシーンへのマッピング、詳細度 (LOD)、ラベル/タグ、カメラコントローラーを備えた、WebGL シーンの抽象化。
* 永続化: ベースラインのシードキャッシュ、シナリオ、診断イベントのための IndexedDB リポジトリ。軽量な設定には localStorage を使用。
* 本番サービスへの依存なし: ネットワークアダプターはインターフェースの背後に置き、将来のリアルタイムソースがプレゼンテーションロジックを書き換えることなくシードプロバイダーを置き換えられるようにします。

# 15. 本番ディスカバリーでのギャップ / 意思決定事項

* 実際の SATS/Changi のソースインターフェース、ソースシステムの識別子、イベントスキーマ、鮮度/レイテンシの契約を確認する。
* 権威ある役割/アカウンタビリティのマトリクスと、Control Tower Lead / オーナーの指名を確認する。
* 2D/3D での利用が許可される実際の空港の空間モデル、座標系、マップ/3D アセットの権利、制限区域 (airside) のセキュリティ上の制約を確認する。
* 正確な SLA の定義と、航空会社固有のマイルストーンのルールを確認する。出典では一部の目標値が未定 (TBC) のままである。
* 本番環境の ID、認可、保持、監査、プライバシーの要件を確認する。ブラウザーストレージはプロトタイピング専用である。
* 本番の 3D レンダリングスタックを確定する前に、パフォーマンス目標と、代表的なピーク時のエンティティ量を確認する。

# 16. このプロトタイプの完了の定義

* セクション 7 のすべてのエンティティタイプが、UI 上にデータが投入され、検索可能になっている。
* セクション 3 のすべてのロールレンズを、単一のデータストアからデモできる。
* 2D と 3D のビューが同期しており、選択、レイヤーコントロール、ズームをサポートする。3D はダイナミックカメラのコントロールをサポートする。
* セクション 6 の 5 つ以上のシミュレーターケースが、パラメーターを検証し、非破壊的な Baseline/Scenario/Difference のビューを生成する。
* どのシミュレーターの操作シーケンス、ページの更新、シナリオの削除の後でも、ベースラインのレコードは変更されない。
* 重要なワークフローが、アクセシビリティとレスポンシブの要件を満たす。
* 表示されるシミュレート値/導出値はすべて、明示的にラベル付けされ、そのパラメーターまで追跡できる。
